01

Spec-Driven and Test-Driven Development規格驅動與測試驅動開發

Turn intent into a spec, then turn the spec into tests that run before the code exists.先把意圖寫成規格，再把規格變成「程式碼還沒寫就能先跑」的測試。

Verified against kiro.dev on 2026-11-25.於 2026-11-25 依 kiro.dev 官方文件查核。

Why vibe coding breaks down為什麼「憑感覺寫程式」會出問題

Intent gets lost意圖走樣

On multi-file work the agent fills gaps with guesses you never see.在跨多個檔案的工作中，agent 會用你看不到的猜測去補空白。

No traceability無法追溯

Why a choice was made lives in a chat transcript, not in the repository.為什麼這樣做的理由只留在對話紀錄裡，不在 repo 裡。

Drift逐漸偏離

Each iteration moves a little further from what was asked.每次迭代都離原本的需求更遠一點。

Self-graded tests自己出題自己改

When one agent writes the code and its tests in one go, the tests tend to confirm the code rather than the requirement.同一個 agent 一次寫完程式和測試時，測試往往在驗證程式碼本身，而不是驗證需求。

Spec-driven development fixes the first three. Test-driven development fixes the fourth.規格驅動開發解決前三個問題，測試驅動開發解決第四個。

SDD and TDD: two halves of one loopSDD 與 TDD：同一個循環的兩半 Recommended pattern建議做法

Spec-driven development (SDD)規格驅動開發（SDD）

  • Answers: are we building the right thing?回答：我們做的是對的東西嗎？
  • Intent → requirements → design → tasks, reviewed before any code.意圖 → 需求 → 設計 → 任務，寫程式之前先審過。
  • Kiro feature: Specs.對應的 Kiro 功能：Specs。

Test-driven development (TDD)測試驅動開發（TDD）

  • Answers: did we build it right?回答：我們有把它做對嗎？
  • Each acceptance criterion becomes a test that fails first (Red), then passes (Green), then stays green while you clean up (Refactor).每條驗收標準都變成一個測試：先失敗（紅燈），再通過（綠燈），整理程式碼時一直保持綠燈（重構）。
  • Kiro building blocks: property-based testing, Bugfix Specs, hooks, Workflows.可用的 Kiro 元件：property-based testing、Bugfix Spec、hooks、Workflows。
Honest framing: Kiro has no feature named “TDD”. This course combines real Kiro features into a recommended pattern, and labels the parts that are a pattern rather than a product feature.誠實說明：Kiro 並沒有名為「TDD」的功能。本課程把 Kiro 真實存在的功能組合成一套建議做法，凡是「做法」而不是「產品功能」的部分都會標示出來。

The loop this course teaches本課程教的核心循環 Recommended pattern建議做法

1 · Requirements1 · 需求Written in EARS; every criterion is testable and has an ID.用 EARS 寫；每條標準都可測試、都有編號。
→
2 · Design2 · 設計Kiro extracts properties; Analyze Requirements finds gaps.Kiro 抽出 properties；Analyze Requirements 找出漏洞。
→
3 · Red3 · 紅燈Write the failing test for one criterion; review and commit it.針對一條標準寫失敗的測試；審過後 commit。
→
4 · Green4 · 綠燈Smallest implementation that passes.用最小的改動讓測試通過。
→
5 · Refactor5 · 重構Clean up with every test still green.在所有測試保持綠燈的情況下整理程式碼。
→
6 · Gate6 · 把關Hooks run tests after each task; CI blocks the merge.Hooks 在每個任務後跑測試；CI 擋住合併。

Pick the right spec type選對規格類型

Requirements-First需求優先

You know the behaviour and the architecture is flexible. Most product features.你清楚要什麼行為、架構還有彈性。大多數產品功能都屬於這類。

You have an existing design, or strict non-functional limits such as latency or compliance.你已經有設計，或有嚴格的非功能限制，例如延遲或合規。

A defect in a critical path, a root cause that isn't obvious, or earlier fixes that caused regressions.關鍵路徑上的缺陷、根因不明顯，或之前的修正造成過退化。

Before you write tests: Analyze Requirements寫測試之前：先分析需求

Red → Green → Refactor, with an agent和 agent 一起做「紅 → 綠 → 重構」 Recommended pattern建議做法

🔴 Red🔴 紅燈

  • The agent writes a test for one criterion, from the requirement — not from existing code.agent 針對一條標準寫測試，依據的是需求，而不是現有的程式碼。
  • Run it. It must fail, and for the expected reason (an assertion, not an import error).執行它。它必須失敗，而且要因為預期的原因失敗（斷言失敗，而不是 import 錯誤）。
  • A person reviews the test, then commits it.由人審過這個測試，再 commit。

🟢 Green🟢 綠燈

  • The agent writes the smallest change that passes.agent 寫出能讓測試通過的最小改動。
  • No edits to the test in this step.這一步不准改測試。
  • Run the whole suite, not just the new test.跑整套測試，而不只是新的那個。

🔵 Refactor🔵 重構

  • Improve names and structure with every test green.在全部綠燈的情況下改善命名和結構。
  • Re-run the suite after each change.每次修改後都重跑測試。
  • Update the spec if you learned something new.如果學到新東西，就更新規格。
The human review of the red test is what stops an agent from grading its own homework. Don't skip it.人工審查紅燈測試，是防止 agent「自己出題自己改」的關鍵步驟。不要跳過。

Key takeaways重點回顧

Spec before code先規格再程式碼

Write EARS criteria you can test, and fix ambiguity before the first test.寫出可測試的 EARS 標準，在寫第一個測試之前就消除模糊。

Red is reviewed紅燈要審查

A person approves each failing test before implementation starts.實作開始前，每個失敗的測試都由人核准。

Properties, not only examples不只範例，還要 properties

Use property-based testing in the IDE, and review properties like code.在 IDE 使用 property-based testing，並像審程式碼一樣審查 properties。

Gates you can't skip跳不過的關卡

Steering guides, hooks give feedback, and required CI checks block.Steering 負責引導，hooks 負責回饋，必過的 CI 檢查負責阻擋。

Scale with structure用結構來規模化

Workflows, sub-agents and headless runs keep the loop as the work grows.Workflows、sub-agent 和無頭模式讓工作變大時循環依然成立。

Stay current保持更新

Check the changelog; Kiro changes almost every week.記得看更新日誌；Kiro 幾乎每週都有變動。

Test-first checklist for your next spec下一份規格的先測試檢查清單

Before code寫程式之前

  • Every criterion has an ID, a trigger and an observable result.每條標準都有編號、觸發條件和可觀察的結果。
  • Analyze Requirements run; ambiguities resolved.已執行 Analyze Requirements，模糊之處已解決。
  • Properties reviewed and strengthened.Properties 已審查並強化。
  • Test tasks come before implementation tasks.測試任務排在實作任務之前。

Before merge合併之前

  • Each red test was reviewed and committed before its implementation.每個紅燈測試都在對應實作之前審過並 commit。
  • No test was weakened or skipped to get green.沒有為了變綠燈而放寬或跳過任何測試。
  • The suite is green in a required CI check.整套測試在必過的 CI 檢查中通過。
  • tasks.md is synced with what was built.tasks.md 已和實際做出來的內容同步。
